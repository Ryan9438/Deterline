## 〇、一页话结论

1. **页内重排是当前唯一同时满足三条硬约束的中文渲染方案**：不新增字体资产（约束①）、不新增纹理页（绕开约束④"新页不加载"）、Texture 指针全部指向原有页。
2. **但 C3b 报告 §四 的原 sketch 有一个必须先修正的容量错误**：它给的"剩余空间可容 ~4290 字"是**全页十个字体区域空闲的总和**；而 glyph 坐标是 TPI 相对坐标（本文 §1 实证），每个字体只能取到**自己 TPI 矩形内**的像素——三个改造目标（ja_main/maintext/plain）自身空闲合计只有 ~1400 格，装不下 4068 字的固定表。**修正方案 = "共享图集 + 页内重指向"**（§3）：把 ja_main 的 1024² TPI 区域整区重排为一张 12px 共享图集（容量 6084 ≥ 4068），三个字体的 Texture 全部指到这一张图（同页内改指针，页身份不变），main 用 ScaleX/Y=2 整体放大。零新增资产、零新页、TPI 矩形不动。
3. **最小复测实验可以做到 1 次 boot 分离两个变量**（§4）：一个 boot 里放 1 个对照臂 + 3 个实验臂（页内×修复后表、main/Scale 臂、原表×新页臂），每个臂对应不同 NPC/typer，结果互不污染。修复后 glyph 表（排序+去重）从未进过游戏的问题、页内重排的核心前提、Scale 是否生效、越界采样是否被钳位——四问同 boot 有答案。预算 ≤5 boot 完成落地或判死。
4. 约束②（折行）落点 = **生成器层共享折行 util + 硬 lint**（§5）；约束③（global.language≠zh）在**无条件映射方案下降级为"无需解决"**（§6），只补一次裸文件名语言探针结案。
5. C3b 应排在 O2 之前，理由是**依赖方向**而非偏好：C3b 不依赖 O2 的任何产物，O2 依赖尚未建成的 V4/O7 护航；且 C3b 剩余工作可以刻意做到"tools/ 优先"，modify_save.py 净增 <150 行，不显著加重拆包负担（§7）。
6. 止损线（§8）：B1 综合判别 boot 中"对照臂绿 + 页内臂全空"且经一次静态复检与一次复测仍空 → 页内重排判死 → 可选 4096 页探针（1 boot）→ 仍死则字体路线冻结，切"逐字精灵渲染层"或搁置；字形资产设计为渲染层无关，沉没成本锁死在 ~3 工作日。

## 一、会前独立验算的两个硬事实（决定方案形态）

### 1.1 glyph 坐标是 **TPI 相对坐标**（实证，非假设）

用 fonts_dump.json（20 字体全量 glyph）核对每个字体的 glyph 坐标范围 vs 其 TPI 矩形：

| 字体 | TPI 在页上的位置 | glyph 坐标范围 | 结论 |
|---|---|---|---|
| fnt_maintext | emb19 (768,0) 256×256 | x:[1,254] y:[2,230] | **相对坐标**（绝对解释会撞进 fnt_main 区域，原版游戏即乱码，不成立） |
| fnt_curs | emb18 (2,394) 256×128 | x:[2,252] y:[2,126] | 同上 |
| fnt_ja_main | emb20 (0,1024) 1024×1024 | x:[4,1020] y:[4,840] | 相对坐标 |

工具侧佐证：font_cjk_atlas.py L129-131 注释"坐标改写为 TPI 相对——引擎按 TPI 区域内相对坐标取字形"。
推论：**一个字体的 glyph 只能采样到"自己 TPI 矩形"内的像素**——除非引擎不按 TPI 钳位（此为待测假设 U2b，§4 可顺带测）。这条事实直接否决了"CJK 网格随便填页面上任意空闲像素"的读法。

### 1.2 C3b 报告 §四 的"~4290"是**总和口径**，按字体分配不成立

对 emb#20 十个字体区域逐字体算空闲（底部自由带 + 每行行尾散闲，14×14 格）：

| 字体 | TPI | 行数/底部 | 自身空闲容量 14×14 | 28×36 格 |
|---|---|---|---|---|
| fnt_ja_main | 1024×1024 | 21 行，底 840 | 949+25 = **974** | 180 |
| fnt_ja_maintext | 512×512 | 21 行，底 420 | 216+7 = **223** | 36 |
| fnt_ja_plain | 512×512 | 20 行，底 440 | 180+19 = **199** | 36 |
| fnt_ja_comicsans_big | 1024×1024 | 20 行，底 640 | 1971+67 = 2038 | 360 |
| fnt_ja_papyrus | 1024×512 | 16 行，底 416 | 438+48 = 486 | 72 |
| fnt_ja_comicsans | 512×512 | 22 行，底 396 | 288+20 = 308 | 54 |
| fnt_ja_curs / papyrus_btl / plainbig / plainsmall | — | — | 212 | 45 |
| **三改造目标合计** | | | **≈1396** | **252** |
| **全页十字体合计** | | | **≈4594** | 783 |

- 固定表（RV-B 修复口径）：ASCII 95 + 假名 191 + CJK（GB2312 一级 + 全角标点去重）≈ 3782 = **4068**（简报记 4064，差异为标点去重口径，不影响结论）。
- 报告 §四 的 "~4290" 与本席算出的 4594 量级吻合——但它把十个区域的空闲当成了一个池子。**按字体分配后，三个改造目标各自只有 223~974 格，装不下 4068**；"ja 原 780 glyph 原坐标重贴 + 各自填空"的字面执行方案，只能覆盖 ~1400 常用字（还是 12px 的；main 需要 28×36 大格，只剩 180 格）。
- **结论：页内重排要成立，必须"整区重排 + 多字体共享同一张图集"**，而不是"各自填自己的空"。这把方案从"贴补丁"升级为"重建一个区域"，但换来的是容量上真正的可行（见 §3.2）。此修正是本席对 C3b 报告的实质贡献之一，建议修订报告 §四后再动工。

关键确认（p3b_output.log "users of emb#20 TPIs" 全表）：

## 三、页内重排工程计划（A1 方案：共享 12px 图集 + 页内重指向）

### 3.1 架构

**改动清单（全部就地改写，零新增资产：Fonts=20、EmbeddedTextures=26、TexturePageItems=6550 全不变）**

| # | 改动 | 内容 |
|---|---|---|
| 1 | emb#20 像素 | 仅重写 (0,1024)-(1023,2047) 象限为 12px 共享图集（13×13 格）；页内其余 3/4 逐字节不动 |
| 2 | 图集内容 | ASCII 95：像素+度量**从原版 fnt_maintext（emb19 dump）原样拷贝**（外观零回归）；假名 173：像素从原版 maintext 拷贝 + 缺失 ~18 个假名由 Fusion Pixel 补；CJK ~3782：Fusion Pixel 12px（白+直通 alpha，遵侦察 §3d 像素惯例）；全表按码点升序、advance：ASCII=原 shift，CJK=12 |
| 3 | fnt_ja_main | Texture 不变（#6543）；Glyphs 全量重写 = 共享表；ScaleX=ScaleY=2（试验位，见 R1） |
| 4 | fnt_ja_maintext | Texture **重指向 #6543**（同页内）；Glyphs = 同一张共享表；Scale=1 |
| 5 | fnt_ja_plain | Texture **重指向 #6543**；Glyphs = 同一张共享表；Scale=1 |
| 6 | scr_setfont | 无条件映射三行（plan_d 已写好并演练过的注入形态：`if (newfont == fnt_main) newfont = fnt_ja_main;` ×3，插在 `draw_set_font(newfont)` 前） |
| 7 | scr_preload_textures | 无条件追加 `sprite_prefetch(spr_fonts_ja_preload);`（**既有**精灵、**既有**页——与 vanilla ja 分支完全同款调用，不是 PD 失败的"新页 prefetch"） |
| 8 | 不动 | 其余 7 个 ja 字体、全部英文字体、emb#19、TPI 矩形、字体数、页数 |

**为什么这个形态可行（逐条对应已证事实）**：
- 页身份不变 → 约束④（新页不加载）不在作用路径上；emb#20 本就是引擎会加载的页（BY 实验中日文页资源在位时基线渲染正常）。
- 字体数不变 → 约束①（20 字体固定表）不触发。
- glyph 表就地替换 → PW 已证明"替换 glyph 列表"本身可启动不炸（当时全空归因于新页）。
- 三个字体共享一份表/像素 → 坐标相同（相对 #6543），per-font 的 shift/offset 仍可各自微调（表是每字体一份的）——这是 advance 校正的零成本调节旋钮。
- ASCII/kana 像素取自原版 → 无条件映射下 en/ja 用户的 ASCII 外观与度量零回归（maintext/plain 完全同像素；main 走 Scale2 = 12px 切片的整数 2 倍，与原 24px 切片同族， advance 2×12px-shift ≈ 原 24px-shift，实测样本核对：! 6×2=12 vs 原 12；# 8×2=16 vs 原 16）。

### 3.2 容量验算（A1）

| 项 | 数值 |
|---|---|
| 图集区域 | 1024×1024 = 1,048,576 px²（ja_main TPI 区域） |
| 固定表需求 | 4068 字形 × 13×13 = 686,816 px² → **填充率 67%，余量 2016 格** |
| cell 14×14 备选 | 5329 格 ≥ 4068（76%）——若 13px 格出现字形蹭边再放宽 |
| 扩展上限 | +GB2312 二级全量 3008 字 = 7076 > 6084 ✗；**L1 + 二级常用 ~2000 字可扩**（cell13） |
| 页外自由矩形（可选 A2） | 512×640 @ (1536,1408)：14×14 格 ≈ 1620 格，仅当 §4 的越界采样假设 U2b 证实后启用 |

字号说明：main（emSize 22）在 Scale2 下 CJK 12px→24px 渲染，与原 ja CJK 28px 略窄但同框；maintext（emSize 11）/plain（emSize 12）1:1。**对话主力是 maintext（NPC 默认 typer 5，55 处引用）与 plain，main 是叙述/战斗（27 处）——12px 类才是 ChatBox 内容的关键路径**，A1 对 12px 类是 1:1 原生渲染，无任何缩放疑虑。

### 3.4 启动实验矩阵设计——怎么少烧 boot

三条省 boot 原则（域F 15 次矩阵的教训制度化）：
1. **单 boot 多臂**：一次启动里用互不相同的 NPC/typer 承载多个实验臂，结果同屏互证（每臂独立可判定）；
2. **预写判定树**：每个臂的每种结果都预先映射到唯一下一步，禁止"看到现象再想"；
3. **静态门前置**：S4 断言不绿不烧 boot——boot 只用来回答"引擎黑盒"问题，不用来抓注入 bug。

**B1 综合判别 boot（1 次启动，4 臂）**

| 臂 | 载体 | 走到的字体/页 | 回答的问题 | 预测 |
|---|---|---|---|---|
| Ctrl | NPC typer 3（fnt_curs，**不在映射内**） | 原字体原页 | 环境/基线绿（本次 boot 本身有效） | ✅ |
| Arm-C ★ | NPC typer 5（生成器默认）→ fnt_ja_maintext@共享图集 | 页内图集 | **页内重排核心前提** + 修复后 glyph 表首次实战 + 重指向 | GO/NO-GO 主判据 |
| Arm-M | NPC typer 0 → fnt_ja_main@图集 Scale2 | 同上 | ScaleX/Y 是否被 runner 尊重；advance×Scale 是否成立（字距目视） | 三种结果均可用（见 R1） |
| Arm-N | NPC typer 30（冷门 case，本 boot 无自然触发）→ fnt_ja_papyrus_btl@**新页**（原表原像素搬运，纹理/TPI 新增、字体零新增） | 新页 | **约束④证伪试**：原表×新页能否渲染（PC/PV/PW 全空是否纯因 glyph 表 bug） | 预期空；若 ✅ 则新页路线复活 |
| 顺带 | 消息内含金丝雀码位（图集表外的 BMP 码位，其 glyph 条目坐标指到页外自由矩形） | 越界采样 | U2b：引擎是否按 TPI 钳位 glyph UV → 决定 A2 扩容路线 | 可选收获 |
| 顺带 | 裸文件名语言探针（bootv 缺陷修正版） | — | 约束③ 直接测量结案 | 记录 |

**B1 判定树（预写）**：
- Ctrl ❌ → 环境问题，修环境重烧（不计入结论）。
- Arm-C ✅（中英都出）→ **GO**：页内重排成立 → S6 集成（B2/B3）。Arm-M/Arm-N/金丝雀作为附加记录各自归档。
- Arm-C 空但 ASCII 出（✱ 情形复现）→ glyph 查找/像素问题：静态复查 CJK 段坐标与表序 → 修 → ≤1 次复测 boot；两次不中 → 按 L1 止损。
- Arm-C 全空、Ctrl ✅、Arm-N ✅ → 矛盾（新页反而通）→ 注入层 bug 概率最大 → 静态复检，不烧新 boot。
- Arm-C 全空、Ctrl ✅、Arm-N 空（预期组合）→ 字体路径对页内像素/重指向同样钝感 → 静态复检 1 轮 + 1 次复测 boot → 仍空 → **页内重排判死** → 4096 页探针（1 boot：emb#20 原布局改 4096²，页身份仍不变）→ 仍空 → 字体路线冻结（§8）。

**boot 预算**：B1（1）+ GO 后 B2/B3（2）+ 迭代备胎（1-2）= **≤5 boot**。对比：C3b 前期已烧 15+。

## 四、RV-B 修复的最小复测实验设计（变量分离）

**变量矩阵现状**（P=页目标，G=glyph 表状态）：

| | 旧表（重复 95 码点+拼音序+无假名） | 原版有序表 | 修复后表（升序+去重+含假名） |
|---|---|---|---|
| **新页** | ❌ 空（PC/PV，R1-R4） | ❌ 全空（PW；BY 未渲染验证） | **未测 ← 缺口** |
| **旧页（未改造）** | — | ✅（A0/BX 基线） | — |
| **旧页（页内改造）** | ⚠️ 仅 ✱（PC，✱ 来自 fnt_main 回退） | — | **未测 ← 主战场** |

要点：**修复后的表从未进过任何游戏内实验**（RV-B 补注明确要求动工前复测），且"排序已修"与"新页加载"两个变量在 PC/PV/PW 里是耦合的。

**最小分离设计**：B1 一个 boot 同时填两个缺口格，且用**不同字体载体**使两臂独立：
- Arm-C = （修复后表 × 旧页页内改造）：若 ✅，与 PC/PV/PW 的 ❌ 对比即证明"glyph 表修复有效 + 页内路径可行"——两个变量一次同时定案（该臂成立时新页路线即被支配、无需再测）；
- Arm-N = （原版有序表 × 新页）：若 ✅，证明约束④的空框纯因 glyph 表 bug、新页本可加载；若 ❌（预期），维持约束④成立——同时它把"BY 交换纹理未渲染验证"的悬案补上。
- 唯一仍可能缺的格子是（修复后表 × 新页）：只在"Arm-C 失败且 Arm-N 成功"的矛盾组合下才需要补测（1 次追加 boot，注入物与 B1 完全相同、只改一个指针），其余一切结局都不需要它。
- **最小 boot 数 = 1，最坏 = 2。**这是"尽量少的 boot"的解，且每一格结果都直接映射到 §3.4 判定树的唯一分支。

## 五、约束②（无空格 CJK = writer 死循环挂起）的落地点

机理（decompiled/obj_base_writer_Draw_0.txt L316-318）：逐字符绘制中 `if (!vtext && myx > writingxend) script_execute(SCR_NEWLINE)`——换行靠**回扫找空格**；无空格 CJK 长句回扫不终止 → PD 实证挂起（侦察预警 #4 升级为 crash 级）。

**落点裁决：生成器层（npc-dialogue / npc-choice / textdata 写入路径共用 util），不在引擎层修。**

1. **共享折行 util `_fold_cjk_lines()`**（modify_save.py 内，三个生成器共同调用）：
   - 折行预算按 typer 的实际 writingxend 推导：typer 5 = x+20 → view_xview+290 ≈ 270px；12px CJK advance → **默认 20 个全角字/行**（留 10% 余量），ASCII 按共享表逐字 shift 累计精确计算；
   - 折行方式 = 在折点插入空格（writer 现行机制的原生折点；行尾/行首不带多余空白由 util 保证——UT 对话按空格断行后由 writer 自己换行，不引入 `\n`，避免 SCR_NEWLINE 未验证行为）；
   - 参数 `--wrap-cols` 可覆盖；`--no-wrap` 显式跳过（自担挂起风险，输出警告）。
2. **硬 lint（防绕过）**：CJK 校验路径（`--allow-cjk` 门）增加不变量——任意"无空格连续 CJK run > cols"直接 reject 并给出折行建议文本。PD 级挂起不允许经任何写路径进入 data。
3. **可选加固（P2，另立决策）**：SCR_NEWLINE 回扫加步数上界（1 行 GML 改动）可根除该类挂起；但按域F 教训，代码改动必须走完整 verify-code + 游戏内验证，不建议与 B1 同包——**先用文本层规则交付，writer 加固作为后续独立项**。
4. ChatBox 侧 SKILL 文档同步：中文对话示例一律带折行说明与 `--wrap-cols` 用法。

## 六、约束③（global.language ≠ zh）在无条件映射下的裁决

**降级为"无需解决"。** 论证：
- scr_setfont 的无条件映射插在语言判断之外（plan_d 形态），对话字体链与 `global.language` 取值解耦——无论 os_get_language 返回什么，fnt_main/maintext/plain 三链都到 fnt_ja_*，再由改造后的 fnt_ja_* 渲染中文。
- preload 同理改无条件追加（对既有页/既有精灵，vanilla ja 分支同款调用）。
- 残余交互面检查：obj_base_writer 的 `global.language=="ja"` 排距分支（Draw_0 L374-403/L584+）在 language≠ja 时不触发 → 中文排距走默认路径，视觉可接受（B1 目视确认项）；若系统真返回 "ja"（日文系统），vanilla ja 分支与无条件映射串联结果一致，无冲突。
- **结案动作**：B1 顺带跑一次裸文件名语言探针（bootv 的 working_directory 拼接缺陷修正：直接 `file_text_open_write("zcode_lang_probe.txt")`），把"≠zh"从联合推断升级为直接测量后归档，该约束不再占用任何后续工作量。

## 七、为什么 C3b 排在 O2 拆包之前

**主论点（按强度排序）：**

1. **依赖方向不对称**。C3b 不依赖 O2 的任何产物（cjk-font 命令今天就能跑）；O2 按路线图自己的依赖律（"O2 拆包依赖 golden tests 护航"、代表2 再加"O7 是 O2 前置"）需要 V4 全量 golden + O7 snapshot-diff 先到位——**两者都还没建成**。所以今天的真实选项不是"O2 vs C3b"，而是"C3b vs 什么都不能安全开工"。先做 C3b 不偷工：它自己带着全套验证纪律（快照+MD5+--commit+verify-code，15 次 boot 演练过）。
2. **用户价值在势能最高点兑现**。中文是 roadmap 自认的"★ChatBox 用户群核心诉求"（研讨会 1 用户价值代表已论证：工具的 SKILL description 尾句今天还在对中文用户说"不支持"）。C3b 现在离终点只剩一个 runner 未知数 + ~3 工作日；此刻切去 O2（2-3 周纯内部工程），回来时管线冷透、上下文重建（15 次 boot 的因果链、10 探针、CSX 全家散在 build/cjk_verify 与两个 AUDIT 目录——这些是"读一遍才敢动"的上下文，不是"读一行"的上下文）。
3. **C3b 的结局无论哪种都让 O2 更便宜**。GO：字体域尘埃落定，O2 拆包时把 cmds/font.py 一并收进去（增量 ~300 行，占 6821 的 4%）；NO-GO：字体命令收缩/归档，拆包范围反而变小。反过来"先 O2 后 C3b"没有任何一种结局让 C3b 变便宜。
4. **判死也是高价值产出**。B1 无论结果如何都给出 runner 字体路径的硬数据（页加载模型/UV 钳位/Scale 行为），这直接喂给 4096 探针、runner 逆向、逐字精灵层三个下游，甚至约束①的"20 字体固定表"猜想也可能顺带收紧。O2 的产出不产生任何新的 runner 知识。

**反方最强论点——诚实评估与对冲：**

- **"6800→7100 行，单文件越拖越难拆"——论点成立，趋势真实。** cjk-font 已为 modify_save.py 净增 ~300 行（L6390-6660 + CSX 模板 + argparse/commands.json）。对冲（不是辩解）：**C3b 剩余工作刻意设计为 tools/ 优先**——图集 in-page 模式（tools/font_cjk_atlas.py）、emb 合成器（tools/）、断言复检脚本（tools/ 或 tests/）、折行 util（虽在 modify_save.py，但是 ~60 行纯函数）；modify_save.py 只加命令薄壳与 CSX 模板常量，**净增承诺 <150 行**，且 O1b 的 commands.json SSOT 已让文档面零增量。同时接受一个约束作为席位承诺：C3b 收尾提交里若 modify_save.py 超过承诺增量，在研讨会记录中认账。
- **"页内重排可能再次被 runner 黑盒判死"——可能，且这正是流程设计的出发点。** 对冲：把证伪放在工程前（B1 先烧 1 boot 回答核心前提，GO 才花 D4 的 1 天；NO-GO 只损失 ≤2 天 + 1 boot，而不是重演"15 boot 才停"）；判定树预写保证判死动作干脆。另须承认：即便 B1 全绿，集成期仍可能遇到新的黑盒（例如页内像素被 runner 缓存于首载——跨 boot 不存在此问题，但如实列为 R 类风险）。判死情形的退出价值见 §8。
- **反方还有一个隐含论点：C3b 判死后逐字精灵层成本高（3-5 天+），可能两头空。** 对冲：字形资产从第一天起设计为渲染层无关（位图 PNG + 度量 JSON + 折行 util 与 UndertaleFont 机制零耦合），逐字精灵层直接吃同一份 atlas——字体路线的沉没成本被锁死在 ~3 工作日，不是白烧。

**给协调者的排序建议**：C3b（D1-D3，≤2.5 天）→ 判定日三者合流：GO 则 D4 收尾后立即开工 O2（此时 V4/O7 可在 C3b 集成期并行补齐）；NO-GO 则 O2 当周开工、字体路线按 §8 处置。O2 没有被"跳过"，只是让出了 3 天。

## 八、止损线（预写，防"再烧 15 boot"）

| 线 | 触发条件 | 动作 |
|---|---|---|
| **L1 路线死** | B1：Ctrl ✅ 且 Arm-C 全空（含 ASCII），静态复检一轮 + 1 次复测 boot 仍全空 | 页内重排判死。可选 4096 页探针（1 boot，emb#20 改 4096² 原布局，页身份不变）：✅ 则容量版页内方案复活；❌ 则**字体路线整体冻结** |
| **L2 部分死** | Arm-C 的 ASCII ✅ / CJK ❌ 连续 2 个 boot 不收敛 | 同 L1 判死（glyph 查找机制不可达，属 runner 黑盒） |
| **L3 预算线** | 本路线累计 boot >5，或工期 >3.5 工作日 | 立即停，转 §8 末段处置 |
| **L4 资产保全** | 任何死线触发时 | 保留入库：图集构建工具、atlas 位图+度量 JSON、折行 util、全部 CSX 与判定树记录——它们是"逐字精灵渲染层"（roadmap §四-4）的直接输入；textdata 层中文备料（C3a 的 --allow-cjk 已落地）不受影响 |
| **冻结期出口** | 字体路线冻结后 | 中文能力二选一：(a) 逐字精灵渲染层 spike（3-5 天，绕开 UndertaleFont 全套机制，机制全在自己手里，吃 L4 资产）；(b) 搁置，保留 C3a 的"诚实预检+行动指南"状态，等待 runner 逆向（路径 3）时机 |

止损线的哲学与域F 一致：**停在"证据烧尽前"，停在"假设被证伪处"**——B1 把最大的假设放在最便宜的实验上，止损线把最贵的沉没成本（一天天的工程）放在证据之后。

## 九、对另外两个席位方案的评价

**工程稳健派（O2 拆包先行）**：对其事实基础给予完全尊重——6821 行、31% 三引号串、5 个子代理重复通读同一文件、door/pit/battle 三胞胎 85% 相似，这些成本是真的，而且**每做一周 C 类能力就再涨一点**。但方案有两处需要修正：其一，按路线图自身的依赖律（O2 ← V4 golden + O7 snapshot-diff），O2 今天不具备安全开工条件，"先 O2"事实上意味着"先 V4+O7 再 O2"，工期前移 1-1.5 周——这恰好是 C3b 的全部工期；其二，先拆后加是二次返工结构：C3b 落地后字体域必然进拆包范围，先拆等于同一批文件动两次。本席的对冲承诺（C3b 增量 tools/ 优先、modify_save.py 净增 <150 行）正是为了把两案从"互斥"变成"串行无损"：C3b 判定日之后，O2 立即开工，且带着一个已收敛的字体域去拆。若稳健派坚持 O2 的第 9 位不能动，本席请其回答一个问题：**拆包完成后第一次大改动如果就是字体域，这次拆包对它的护航价值是什么？**

**风险审计派（先还债/doctor）**：方向健康、成本便宜，且其纪律已经赢了——V2 写入安全、golden CSX、verify-code、O1b SSOT、diff-snapshots、--allow-cjk 都已在本轮会话落地（git log 5e0208e / 722a9f0 / d1e8632），15 次 boot 的"备份+MD5+恢复"纪律正是审计派方法论的成功案例。需要指出的是剩余债务清单（doctor 聚合、O5 目录化、O4 完整 schema、O7 全量结构 diff）**没有一项阻塞 C3b 的实验安全**：C3b 的每一步都被审计派自己建好的护栏（快照、MD5、--commit、verify-code、golden）覆盖。若坚持 doctor 先行：doctor 是 0.5-1 天的纯聚合工作，与 C3b 的 D1/D2（tools/ 日）完全并行不抢人，本席无异议——但请勿让它串行占据关键路径，"还债"的正确姿势是债不阻塞生产时随时还、阻塞时不还。同时提醒：审计派最有力的论据"无声失败比报错更伤信任"恰恰支持 C3b——今天对中文用户最无声的失败，就是 description 尾句那句"must be English/ASCII only"。
